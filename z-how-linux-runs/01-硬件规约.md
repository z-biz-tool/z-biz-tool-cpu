# 01 · 硬件规约：通电之后，发生了什么（彻底版）

> 目标：在 OS 出现之前，理解机器自己怎么动。看懂这一篇，你就站在了 Linux 内核作者的起点。
> 本篇为彻底版：每一步都给到电路与规约的出处——4 条通道各有 mini_machine/cpu_work 对应篇目，随时回查。

## 1. CPU 只会一件事

CPU 没有智慧，它是一个死循环执行器：

```
while (true) {
    指令 = 内存[RIP];        // fetch：按 RIP 取指
    RIP += 指令长度;
    执行(指令);               // decode + execute
}
```

三步逐个展开——每一步都是真实电路，不是比喻（cpu_work 05 造的就是它）：

1. **fetch**：把 RIP 的值放上地址总线 → 内存控制器（MC）收到 → DRAM/SRAM 按地址译码 → 字节沿数据总线返回 → 塞进 CPU 的"指令队列"。
2. **RIP += 指令长度**：x86 指令 1~15 字节不等，长度由第一个字节（opcode）决定——硬件里有专门的"长度解码器"提前算好下一条的位置。RISC 指令定长（如 4 字节），`RIP += 4` 一个加法器搞定——**这就是"定长指令好流水线"的物理原因**（cpu_work 06）。
3. **decode + execute**：按编码表把字节拆成"操作码 + 操作数"，译码器（一组与/非门，cpu_work 05）点亮对应的控制线——ALU 收到"做加法"、寄存器堆收到"读 RAX 写 RDX"、访存单元收到"去 0x2000 取数"。**所谓"执行"，就是译码器把正确的控制线拉高，让各部件在同一拍各干各的。**

它认识的全部世界：指令流、内存地址、寄存器。
它不认识：进程、文件、线程、操作系统——这些全是后面软件造出来的词。

本篇用到两个寄存器，各展开一句：

- `RIP`（下一条指令地址）：唯一推动程序前进的量。**程序 = RIP 的轨迹**；"程序卡死了" = RIP 在几条指令间打转；"程序跑飞了" = RIP 被写到了垃圾地址。
- `RSP`（栈顶指针）：栈不是一块特殊硬件，就是一段普通内存 + 一条约定——`push` = `RSP -= 8; 内存[RSP] = rax`，`pop` 反向。cpu_work 05 说过：**栈的硬件成本是零，全部是"把 RSP 当游标用"的软件约定**。函数调用、中断压栈、局部变量，全靠这根游标。

## 2. 通电：CPU 醒来的第一件事

通电瞬间，电源电压爬升（mini_machine 02：POR 复位控制器拉住一切，直到电压稳定），然后 CPU 复位成 x86 规约的初始状态：

- **16 位实模式**：为了 1981 年的 8086 向下兼容，今天的 64 位 CPU 上电时仍假装自己是那颗 1978 年的芯片——只有 1MB 地址空间、无分页、无保护、任何代码可改任何内存。16 位实模式只是 64 位长模式的"人生第一页"，后面固件会逐级切换上来。
- `RIP = 0xFFFF_FFF0`——4GB 地址空间的顶端附近，距顶只有 16 字节。

两个自然问题，各有一个硬答案：

- **这 16 字节里放什么？** 一条跳转指令 `jmp far`，直接跳到 BIOS 代码主体（顶部 64KB ROM 区）。规约只保证 16 字节，BIOS 自己保证第一件事就是跳走。
- **0xFFFF_FFF0 不是内存条，是谁应答？** 芯片组（北桥/现代 CPU 内置的内存控制器）里有一张**地址路由表**：`0xFFFF_0000~0xFFFF_FFFF` 这个区间不发给 DRAM，而是发给 SPI 总线上的 BIOS ROM 芯片。CPU 发起取指 → 路由表把这次读转向 ROM → ROM 返回字节。**CPU 全程不知道对面是 ROM 还是 DRAM**——地址只是路由标签（mini_machine 00/01 的译码器思想）。

**「规约（protocol）」的含义**：没有任何强制力，只是 Intel 手册和主板厂商之间的约定——CPU 保证从 `0xFFFF_FFF0` 取第一条指令，固件厂商保证把代码放在那里。双方守约，机器就动。OS 领域一半的"魔法"都是这类约定。

## 3. 机器各部分怎么协作（全部通道）

数一数 CPU 和外部世界之间的全部通道，只有 4 条。

### 通道 1：读写内存

`mov rax, [addr]`——内存是一个巨大的按字节编址的数组。但"读一次"底下是一条完整链条（memory_work 01 逐段拆过）：

```
CPU 发地址 → MMU/缓存检查 → 未命中则走总线 → MC 译码出 channel/bank/row
→ 若行未激活：ACTIVATE（tRCD≈10ns）→ READ（CL≈14ns）→ 数据上总线返回
```

应用看到的 ~70-100ns = 激活税 + 排队 + 往返的总和。**内存没有"取货"这个动词，只有"发命令序列"**——MOV 的底下是 ACT/READ/PRE 的命令协议。

### 通道 2：读写设备寄存器（设备的"遥控器"）

每个设备内部都是一个"状态机 + 一组寄存器"（mini_machine 03 的统一形态：控制 CR / 状态 SR / 数据 DR）。CPU 碰它们的两种方式：

- **端口 I/O**：`out 0x3F8, al`——独立于内存的第二套地址空间（64K 端口），用专用指令访问。0x3F8 是传统串口（COM1）的数据口。**两套地址空间的译码器分开**：端口 0x3F8 和内存 0x3F8 是两个地方。
- **MMIO**：把设备寄存器放进内存地址空间。VGA 显存固定在 `0xB8000`：往这个地址写 `0x0748`，芯片组路由表把这拍发给显卡（不是 DRAM），显卡把 `48`（'H'）写进显存单元、把 `07` 记为颜色属性——屏幕左上角立刻出现黑底白字的 H。**对 CPU 这只是一条普通 mov。**

| | 端口 I/O | MMIO |
|---|---|---|
| 地址空间 | 独立 64K | 与内存共用 |
| 指令 | 专用 in/out | 普通 mov |
| 译码 | 端口译码器 | 内存路由表 |
| 现代 CPU 倾向 | 遗留设备（串口/PS/2） | 一切新设备（USB/NVMe/网卡） |

**统一洞见：对 CPU 而言，"控制设备" = "读写某些地址"。设备没有任何特殊地位——它只是把自己伪装成了内存（mini_machine 00）。**

### 通道 3：中断（设备叫 CPU 的门铃）

CPU 顺序执行时是"聋的"——它只看 RIP，不会主动问"外面有什么事"。设备有话要说（数据到了、出错、时钟到点），就拉中断线：

1. CPU **每执行完一条指令**检查中断引脚（不会打断半条指令——指令原子性的物理来源）
2. 有铃 → **硬件自动**（mini_machine 04 逐拍走过）：压栈保存现场（x86 是 SS/RSP/RFLAGS/CS/RIP）→ 查中断向量表（IDT：256 个表项，中断号×8 定位）→ 跳到处理程序
3. 处理完 `iret`：硬件反向出栈，RIP 回到断点，仿佛无事发生

两个此刻就值得记住的细节：

- **每条设备线都有编号**（中断号），编号→处理函数的映射表就是 IDT——mini_machine 04 的"向量表"在大机器上的名字。
- CPU 有办法**暂时捂住耳朵**（`cli` 关中断）——这也是后面一切并发问题的根源之一：关中断期间发生的门铃会排队（pending），处理顺序变成软件课题。

此刻中断还只是个门铃。它是后面一切（调度、驱动、系统调用）的根——**系统调用本质上就是软件主动按自己的门铃**（`syscall` 指令 = 程序自己触发一次受控中断）。

### 通道 4：DMA（设备自己搬数据）

大块数据（磁盘 → 内存）不让 CPU 一个字一个字搬。DMA 控制器是总线上**另一个 master**（mini_machine 01 仲裁 + 04 详解）：CPU 只往它的寄存器里写四个数——源地址、目的地址、长度、触发条件——然后继续跑自己的代码；DMA 硬件在总线上自主搬完，拉一次中断说"完了"。

数量级感受：搬 4KB，CPU 搬运 = 512 条 `mov` + 512 次循环判断 ≈ 几千拍；DMA = 1 次配置 + 1 次中断。**CPU 从搬运工升格为指挥官**——一切高吞吐设备（NVMe、网卡、USB）都靠它。

### 汇总表

| 部件 | CPU 对它做什么 | 它对 CPU 做什么 |
|---|---|---|
| 内存 | `mov` 读/写（底下是 ACT/READ 命令） | 无（被动） |
| 设备寄存器 | `out`/`in` 或 `mov`（MMIO） | 无（被动） |
| 中断控制器 | `out`/`in` 配置（屏蔽、优先级） | 拉门铃 |
| DMA 控制器 | 写命令寄存器（四个数） | 搬完拉门铃 |
| 时钟 | 配置周期 | 按周期拉门铃 |

**就这 4 条通道，没有第 5 条。** 后面 OS 的所有复杂度，都是在这 4 条通道上用软件叠出来的。

## 4. 固件：第一段先我们而存在的代码

BIOS 上电后做的事（POST 自检 → 找启动盘 → 交权），逐条展开：

1. **自检（POST）**：探测内存（往每个地址写再读回比对——通道 1 的用法）、初始化键盘/显卡。往屏幕写字符就是往 `0xB8000` 写——和通道 2 对上了：**固件自己也在用这 4 条通道**。
2. **按启动顺序（boot order，存在 CMOS/NVRAM 里的一张表）**，对每个候选盘：读**第 0 个扇区**（512 字节）到内存 `0x7C00`。读盘用的是 BIOS 自己的磁盘驱动（`int 0x13` 服务）——固件里已经有一小坨驱动代码。
3. **验签**：检查这 512 字节的**最后两字节**是否等于 `0x55, 0xAA`。为什么验尾不验头？——扇区开头 446 字节可能是全零（没装引导器的空盘），只有"刻意做完并填充到 510 字节"的引导扇区才会把 0x55AA 恰好放到末尾。**不签名 = 货物拒收 = 换下一个盘**。
4. **交权**：RIP = `0x7C00`，CPU 开始执行我们的代码。固件退场（它留下的只有：实模式状态 + 一堆 BIOS 服务函数）。

**`0x7C00` 这个怪数字的来历**：1981 年 IBM PC 的最低内存配置是 32KB。设计者把引导扇区放在"32KB 顶部再往下留 1KB 给栈和数据"的位置：`0x8000 − 0x400 = 0x7C00`。后来机器内存大了百倍，这个数字因兼容性被永远封存——**规约的化石层**。

> UEFI 时代换了规约：固件自己认识 FAT 文件系统，读 **ESP 分区**里的 `.efi` 文件（PE 格式可执行），可以按 64 位长模式直接加载。本质不变——**固件的职责就是把控制权交给你的代码**，只是入口从"读第 0 扇区"升级成"认文件系统、读指定文件、验签名"。

## 5. 亲手验证：512 字节的裸机程序

我们写的代码会被 BIOS 装到 `0x7C00` 并执行。此时：16 位实模式，没有 OS，没有 libc，没有 printf。打印字符串两条路：调 BIOS 的视频服务（`int 0x10`），或者自己往显存 `0xB8000` 写。

```nasm
; mbr.asm —— 通电后跑的第一段"我们自己的"代码
[bits 16]
[org 0x7C00]                ; 告诉汇编器：我们会被装到 0x7C00
                            ; （01a 篇②：链接地址 = 装载地址，否则绝对寻址全错）

start:
    mov si, msg             ; si = 字符串地址（实模式：段:偏移，此处简化）
.next:
    lodsb                    ; al = [si++]，取一个字符（DS:SI 指向的字节装进 al）
    or al, al                ; or 自己 = 只为设置 ZF 标志（al==0 则 ZF=1）——测试零的惯用法
    jz .hang                 ; 0 结尾则完事（字符串以 0 结尾是 C 的惯例，此刻已沿用）
    mov ah, 0x0E             ; ah = 服务号 0x0E："以打字机模式显示一个字符"
    int 0x10                 ; 软中断：查 IVT 第 0x10 号 → 跳进 BIOS 的显示服务
                             ; （中断不只设备能用，软件也能主动按铃叫固件函数）
    jmp .next
.hang:
    jmp $                    ; 死循环：$ = 当前行地址，跳到自己 = RIP 原地踏步
                             ; CPU 只会继续取指，它不知道"程序结束了"——
                             ; "结束"是 OS 的概念，裸机上必须自己无限循环

msg db "hello, bare metal!", 0

times 510-($-$$) db 0       ; $$ = 段起点(0x7C00)，$-$$ = 已用字节数；0 填充到 510
dw 0xAA55                    ; 最后两字节：BIOS 认的签名（注意小端：文件里是 55 AA）
```

运行：

```bash
nasm -f bin mbr.asm -o mbr.bin
dd if=/dev/zero of=disk.img bs=512 count=2880     # 一张 1.44MB 软盘镜像
dd if=mbr.bin of=disk.img conv=notrunc            # 写进第 0 扇区（01a 篇③：放置）
qemu-system-x86_64 -drive format=raw,file=disk.img
```

屏幕出现 `hello, bare metal!`——这台"电脑"上没有任何 OS，你的代码就是全部。

更裸的版本（连 BIOS 都不依赖）：显存 `0xB8000` 起是 80×25 个字符格，**每格 2 字节：[ASCII 码, 颜色属性]**——属性字节高 4 位背景色、低 4 位前景色，`0x07` = 黑底白字。往 `0xB8000` 写 `48 07`，左上角立刻出现 H，不需要任何服务调用。**这就是 MMIO：写内存 = 控制世界。**

（`int 0x10` 是 BIOS 这个"迷你固件库"提供的服务——注意它和硬件中断共用同一套机制：IVT 表、压栈、iret。软件中断和硬件中断在 CPU 眼里是同一种跳转，只是按铃的是谁不同。）

## 6. 此刻成立的三个结论

1. **OS 不是必需品**。裸机完全能跑你的代码——OS 是后面为了解决公共问题才出现的（见 02 篇）。mini_machine 05 已预演：需求压力会把裸机程序逼成 OS 的形状。
2. **机器的全部协作 = 4 条通道**（读写内存、读写设备寄存器、中断、DMA）。硬件规约到此讲完，且每条通道都能落到电路（memory_work + mini_machine）。
3. **你已经站在内核作者的起点**：`0x7C00` 之后写什么，机器就做什么。Linux 内核被 GRUB 跳入那一刻，处境与此完全相同——只是它接下来做的事庞大得多。
