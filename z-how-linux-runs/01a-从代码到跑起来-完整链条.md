# 01a · 从一行代码到跑起来：完整链条（彻底版）

> 追问 01 篇：我写了一个小代码，怎么放到一台机子上，它能跑起来？
> 答案是一条六环链。**每一环都是一份规约（约定）**，缺一环机器就不动。
> 彻底版：每一环都拆到字节与指令级，给出"为什么必须存在这一环"的电路理由。

## 0. 链条总览

```
hello.c（文本，人话）
 │  ① 编译/汇编 —— 翻译规约：指令集编码表（Intel 定）
 ▼
机器码字节（obj）
 │  ② 链接 —— 地址规约：定下"我自以为在内存哪里"
 ▼
可执行映像
 │  ③ 放置 —— 放置规约：磁盘第 0 扇区 + 0x55AA 签名（IBM PC 定）
 ▼
磁盘第 0 扇区（仓库，躺着，CPU 碰不到）
 │  ④ 搬运 —— 装载规约：BIOS 读出 → 写进内存 0x7C00
 ▼
内存 0x7C00（上膛，进入 CPU 取指范围）
 │  ⑤ 点火 —— 执行规约：RIP = 0x7C00
 ▼
⑥ 取指-执行循环自然运转 = "跑起来了"
```

先记住两个贯穿全链的事实：

- **CPU 只能从内存取指令**。RIP 是内存地址，不是磁盘地址。所以"放在机子上"（磁盘/ROM）不等于"能跑"，必须先进内存。这就是为什么永远需要一个"搬运者"。
- **代码就是数据**。内存里一切皆字节，"代码"和"数据"的差别只在于**被谁解释**：被 CPU 按指令集编码表解释 = 代码；被编辑器按 UTF-8 解释 = 文本；被编译器按 C 语法解释 = 源码。这是冯·诺依曼架构的全部根基——也是病毒、JIT、自解压压缩包的全部可能性。

## 1. ① 编译 = 查表翻译（三级流水：C → 汇编 → 字节）

严格说是两级：编译器把 C 翻成汇编（仍然是人话，有助记符），汇编器把汇编翻成字节（真正的查表）。

```
C:       putchar('H');
汇编:    mov ah, 0x0E        ; 为 BIOS 打印服务做准备
         mov al, 0x48        ; 'H' 的 ASCII
         int  0x10
字节:    B4 0E B0 48 CD 10   ; 每条指令 2-3 字节，首字节是 opcode
```

汇编器的工作是**纯查表**，逐条对应：

```
源码:   mov ah, 0x0E
编码:   B4 0E                ; B4 = "MOV AH, imm8" 的 opcode；0E 是立即数
        ↑ 查编码表（Intel 手册 Vol.2）
```

访存的例子（在屏幕左上角画一个 'H'）——顺便看清**小端字节序**：

```
源码:   mov word [0xB8000], 0x0748     ; 显存地址写两字节：ASCII 'H' + 黑底白字
编码:   C7 06 00 80 07 48
        │   │  └─┴──┘ └─┘
        │   │   disp16  imm16
        │   └─ ModRM 字节：寻址模式（[disp16]）
        └─ opcode：MOV r/m16, imm16
```

- imm16 = 0x0748 存成 **48 07**：低位字节在低地址——x86 是小端。所有多字节数值（地址、立即数、文件头里的长度字段）都遵守；看十六进制 dump 时必须心里倒着读。
- 地址 0xB8000 编进指令的 disp16 字段……等等，0xB8000 超过 16 位了？——实模式下物理地址 = **段寄存器×16 + 偏移**（20 位地址总线时代的产物）：此处段寄存器 DS=0x8000，偏移 0x3800，0x8000×16 + 0x3800 = 0xB8000。**段机制是 1978 年的地址扩展补丁，今天只剩兼容价值**——这也是为什么固件第一件事就是把它切换掉。

每个字节都有含义，写错一个，CPU 就会把它解释成完全不同的指令（没有任何"这不像合法指令"的检查——CPU 不懂"合法性"，只有查表结果）。`objdump -d` 就是拿编码表反着查给你看的工具。编译器在此之上还做寄存器分配、优化，但本质不变：**产出一串精心排布的字节**。

## 2. ② 链接 = 定下"我自以为在哪"

指令里的跳转地址、访存地址都要填成**具体数字**。填多少，由**链接地址**决定。这一环的必要性看个两文件例子：

```
; main.asm 调用 print.asm 里的函数
main.asm:  call print          ; ← "print" 此刻只是个名字
print.asm: print: mov ah,0x0E ; ← print 在自己文件里的偏移是 0
```

链接器做两件事：

1. **符号解析**：收集所有文件的符号表（print 定义在 print.asm 偏移 0）与重定位表（main.asm 里有一处 call 引用 print）。
2. **重定位**：print.asm 被安排在最终映像的 0x0200 处 → 把 main.asm 里那条 call 的操作数**回填**成 `call 0x0200`。

每个绝对地址都来自这个回填——所以链接地址一变，回填结果全变。**关键坑：链接地址必须等于装载地址**（这里是 `0x7C00`），否则所有绝对寻址都指错地方。MBR 里的 `[org 0x7C00]` 就是在告诉汇编器："我会被装到 0x7C00，按这个基准填地址"。

（伏笔：现代 Linux 程序链接地址是虚拟地址 `0x400000`，运行时才翻译；位置无关代码（PIC）连跳转都用相对偏移，搬到哪里都能跑——03、04 篇展开。MBR 这个坑只是"还没有 MMU"时代的朴素形态。）

## 3. ③ 放置 = 仓库入库

`dd if=mbr.bin of=disk.img conv=notrunc` 的作用：把这 512 字节写进磁盘**第 0 扇区**。逐参数拆解：

- `if=` 输入文件；`of=` 输出文件（一个普通文件模拟的磁盘，或真盘 `/dev/sda`）
- `conv=notrunc`：**不要截断输出文件**——默认 dd 会把目标剪成输入那么大，写引导扇区会把整张盘剪成 512 字节
- 没写 `seek=` → 从偏移 0 写起 = 恰好覆盖第 0 扇区

"第 0 扇区"是什么？磁盘的最小读写单位是**扇区（512B，现代 4Kn 是 4096B）**，物理地址就是扇区号（LBA，memory_work 04）。BIOS 读盘的最小粒度也是一扇区——**512 字节不是随便定的，是双方的最小对话单位**。`0x55AA` 签名在这 512 字节的最后两字节。

此刻它只是仓库里的货。**CPU 碰不到它**——原因重复一遍：RIP 是内存地址，取指循环只对内存工作。躺在磁盘上的字节不是"程序"，只是"待搬运的字节"。memory_work 04 说过：磁盘上"地址即时间"，而 CPU 根本没有"对磁盘取指"的能力——**这是哈佛思想在设备层的残留：取指专属于内存路径**。

## 4. ④ 搬运 = 谁来上膛

上电瞬间，整台机器只有一段代码先在：**BIOS（固件，烧在 ROM 里）**。它不需要被搬运——因为 ROM 被芯片组直接映射到 `0xFFFF_FFF0`，CPU 复位后取指就落在它身上（01 篇 §2 的地址路由表；mini_machine 02 的"复位第一拍"）。

BIOS 按规约做四件事：

1. 读启动盘第 0 扇区（512 字节）——它自己的驱动在跑（通道 1+2 组合：写磁盘控制器寄存器、等中断）
2. 写到内存 `0x7C00`
3. 验最后两字节 == `0x55 0xAA`（不签名的货物拒收，试下一个盘）
4. RIP 指向 `0x7C00`

注意 BIOS 的四件事全部只用 01 篇的通道 1/2/3——**搬运者不是特权角色，只是恰好在场的第一段代码**。

注：这是 IBM PC 的规约。单片机（mini_machine 02：取向量表前 8 字节）、树莓派、UEFI 的规约各不相同，但"**搬运者把代码搬进 CPU 的取指范围**"这一步永远存在，变的只是搬运者和目标地址。

## 5. ⑤+⑥ 点火 = RIP 指过去，循环自然转

"程序开始运行"**没有任何仪式**：RIP = 0x7C00，下一拍取指循环就从那里取字节、按编码表解释、执行。所谓"在跑"，就是 RIP 一次一次更新、指令一次一次被读进 CPU。

执行中一条指令的完整旅程（把 01 篇的通道 1 全部点亮）：

```
RIP 放上地址总线 → 芯片组路由 → MC → DRAM 译码 row/col → 字节返回
→ CPU 译码（查表：这是什么操作、动哪些寄存器）
→ 控制线拉高 → ALU/寄存器堆/访存单元各就各位
→ 写回（可能又是一次访存）→ RIP 更新 → 下一拍取指
```

特例：写 `0xB8000` 那条指令时，地址 `0xB8000` 被芯片组**路由到显卡**而不是内存条——**地址同时是路由标签**。这就是 MMIO 的本质：地址空间是一张"谁应答这个号"的路由总表，CPU 对应答者的身份毫不关心。

## 6. 对齐 Linux：./a.out 走的是同一条链

| 环节 | 裸机 | Linux |
|---|---|---|
| ① 翻译 | nasm/gcc → 平字节 bin | gcc → ELF 文件（多了个格式外壳，本质同） |
| ② 链接 | org 0x7C00 | 链接脚本定虚拟地址（默认 0x400000 附近） |
| ③ 放置 | 磁盘第 0 扇区 | 文件系统里的普通文件 |
| ④ 搬运 | BIOS 手搬 512B | 内核 execve：建页表映射（甚至可以不真搬字节，04 篇见分晓） |
| ⑤ 点火 | RIP = 0x7C00 | 新进程的 RIP 指向 ELF 入口地址 |
| ⑥ 执行 | 取指-执行循环 | **同一个循环，CPU 根本不知道区别** |

ELF 外壳多给了什么？看它的头几个字节：`7F 45 4C 46`（魔数 `.ELF`）+ 一张段表——声明"哪些字节是代码、哪些是数据、各自希望放在哪个虚拟地址、入口在第几偏移"。内核的 execve 读这张表照单办理。**MBR 的"规约"只有 512B+签名一条，ELF 的规约是一整张货单**——货越杂（代码/数据/符号/重定位信息），单子越厚，本质不变。

**"加载 = 把字节搬进 CPU 取指范围 + RIP 指过去"——这个本质从裸机到 Linux 一字不变。** 书里讲 execve、动态链接器时，你手里已经有它们的裸机原型了。

## 7. 归约检验

问：这台机器上真正发生了什么？

- 编译、链接发生在**另一台机器**上（你的开发机）——它们不在这台机器的执行链条里，是"把人话变成字节"的离线工序
- 这台机器上只有：BIOS 的搬运（一堆 mov + 中断）+ CPU 的取指-执行循环

全部归约到根能力：mov + 总线读 + RIP 更新。没有任何新东西。

## 8. 本篇结论

1. "跑起来" = 字节进内存 + RIP 指向它。没有仪式，没有魔法——第 6 节的旅程逐拍可查。
2. 六环链的每一环都是规约：编码表（Intel 定）、扇区 0 + 0x55AA（IBM 定）、0x7C00（IBM 定）、RIP 取指循环（CPU 硬件实现）。**规约越厚，生态越复杂，但"搬运者 + 点火"的骨架不变**。
3. 你现在可以精确回答：**"为什么程序不能直接在磁盘上跑？"**——因为 RIP 是内存地址，CPU 不对磁盘取指；任何代码都必须先被某个搬运者放进内存。
4. 小端、段机制、ELF 货单——都是链条上的历史沉积物：**每层规约都为某个当年的硬件约束而生，然后被兼容性封存**。
